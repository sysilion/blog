## 무슨 일이

chicle은 라이브 채팅을 받으면서 30초마다 하이라이트를 다시 계산했다. 계산은 다시보기 분석과 같았다. 받은 채팅 전부로 반응 점수를 내고, 방송 길이에 따라 정한 개수(1시간당 2개, 최소 5, 최대 20)만큼 상위 피크를 고른다. 끝난 방송 두 개를 5분 간격으로 다시 흘려 보니 화면에 뜨는 목록이 계속 바뀌었다.

| | 10.6시간 방송 | 6.1시간 방송 |
| --- | --- | --- |
| 한 번이라도 뜬 후보 | 27 | 30 |
| 떴다가 최종에서 빠진 후보 | 7 | 18 |
| 가장 오래 떠 있다 빠진 후보 | 50분 | 4시간 15분 |
| 장면보다 1시간 넘게 늦게 뜬 후보 | 7 | 2 |

메모리도 방송 길이를 따라 늘었다. 19만 건 방송은 원본 채팅만 53MB였고, 한 번 계산하는 데 6.1초와 순간 74MB가 더 들었다.

## 원인

상위 N개 고르기는 끝까지 다 본 다음에 하는 [[오프라인 알고리즘]]이다. 라이브는 그때그때 정해야 하고, 한 번 보여 준 것을 거두지 않아야 한다. 그런데 매번 처음부터 다시 고르니 세 가지가 겹쳤다.

- 나중에 더 센 장면이 나오면 정원 밖으로 밀린다.
- 평상시 기준이 방송 전체 평균이라, 초반에 튀어 보이던 구간이 나중에 기준 아래로 내려간다.
- 정원이 방송 길이에 따라 늘어나서, 순위가 조금 밀렸던 지난 장면이 몇 시간 뒤에야 들어온다.

## 재현

끝난 방송의 채팅을 시각순으로 잘라 넣고, 컷마다 분석해 하이라이트 목록을 모은다.

```python
cut = start + 300
while cut <= end:
    rt.chats = [c for c in chats if c[0] <= cut]
    rt.now_sec = lambda c=cut: c
    manager._analyze_locked(rt, final=False)
    history.append((cut, [h["timestamp"] for h in rt.result["highlights"]]))
    cut += 300
# 같은 후보(±60초)가 몇 컷 동안 떠 있었는지, 최종에 남았는지 센다
```

## 그래서

라이브 판정을 따로 만들었다.

- 채팅이 들어올 때 초 단위 점수를 바로 더해 두고, 원본은 최근 30분 치만 둔다.
- 새 후보는 최근 25분 안에서만 찾는다. 하한은 "지금까지 받은 구간에서 1시간당 3번째 안에 드는 피크"다. 표준편차의 몇 배로 하한을 잡았더니 방송마다 결과가 크게 달랐다(3배일 때 15개, 52개).
- 10분 동안 남은 후보는 확정하고, 다시 계산하지 않는다. 받기 시작하고 15분 동안은 예비로만 보여 준다.
- 처음 걸렸을 때 이미 5분 넘게 지난 장면은 띄우지 않는다.
- 고액 후원 구간은 개수 상한과 따로 센다.

같은 두 방송을 1분 간격으로 다시 흘린 결과, 확정한 뒤 사라진 하이라이트는 0개였고 장면이 처음 뜨기까지는 2분 이내였다. 19만 건 방송이 들고 있는 양은 7MB, 한 번 계산은 평균 0.16초로 줄었다. 방송이 끝나면 원본 전체로 한 번 다시 계산해서 다시보기 분석과 같은 결과를 남긴다.

## 한 줄

끝까지 보고 고르는 규칙을 실시간 화면에 쓰기 전에, 지난 데이터를 시각순으로 흘려 목록이 얼마나 뒤집히는지부터 센다.
