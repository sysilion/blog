[AutoMMD](https://github.com/sysilion/AutoMMD)는 실사 영상에서 사람 동작을 추출해
MikuMikuDance 모션 파일(`.vmd`)로 바꾸는 파이프라인이다.

```text
YouTube/MP4 → 사람 인식 → 3D 관절 → 스무딩 → 접지·궤적 → 본 회전 → 키 정리 → .vmd
```

Blender를 띄우지 않고 순수 Python으로 처리한다. 아래는 만들면서 **실제로 발목을 잡았던
지점들**과 그 대응이다. 튜토리얼이 아니라 연구 노트에 가깝다.

## 1. 파이프라인을 파일 경로로만 잇는다

각 단계가 함수 호출이 아니라 **파일**로 연결된다. `extract`가 스켈레톤 JSON을 뱉고,
`export`가 그걸 읽어 [[vmd]]를 만든다.

```bash
python -m autommd extract -e mediapipe -i dance.mp4 -o out/skeleton.json
python -m autommd export  -i out/skeleton.json -o out/dance.vmd
```

한 단계가 무거우면(추출은 분 단위) 뒤 단계를 반복 실험할 때 앞을 다시 돌리지 않아도 된다.
추출기 교체도 규약 하나로 끝난다 — `(video_path) -> SkeletonSequence` 함수 하나를 구현하고
`extractors/__init__.py`에 등록하면 이후 단계가 그대로 재사용된다.

덕분에 **의존성 없이 전체 경로를 검증**할 수 있다. `mock` 추출기가 합성 모션(팔 스윙, 무릎
굽힘, 바운스)을 만들어내므로 MediaPipe도 영상도 없이 리타겟·VMD 경로가 돈다. CI에서 무거운
모델을 받지 않고도 회귀를 잡는다.

## 2. VMD는 Shift-JIS 고정 길이 레코드다

VMD 0002는 1990년대 감성의 바이너리다. 본 프레임 하나가 **111바이트 고정**이다.

```python
# 이름15 + frame(u32) + pos(3f) + rot(4f) + 보간64 = 111바이트
_BONE_FRAME = struct.Struct("<15sI3f4f64s")
_MORPH_FRAME = struct.Struct("<15sIf")   # 모프는 23바이트, 보간 곡선이 없다
```

여기서 두 가지가 걸린다.

**본 이름을 바이트로 자르면 안 된다.** 이름 칸은 15바이트인데 인코딩은 [[shift-jis|Shift-JIS]]다.
`左ひじ` 같은 이름은 글자당 2바이트라, 15바이트에서 무심코 자르면 마지막 글자가 반쪽만 남아
디코드가 깨진다. 한 글자씩 넣다가 넘치면 멈추는 수밖에 없다.

```python
for ch in name:
    encoded = ch.encode("shift_jis", errors="replace")
    if len(raw) + len(encoded) > length:
        break
    raw += encoded
```

**보간 곡선 64바이트는 매직 넘버다.** MMD 기본 선형 곡선은 `20, 20, 0, 0, 20, 20, ...107...`
로 이어지는 고정 바이트열이다. 의미를 따지기보다 표준값을 상수로 박아두는 편이 안전하다.

성능은 단순한 데서 나왔다. 본 이름은 14종 안팎이 수만 번 반복되므로 Shift-JIS 인코딩 결과를
캐시하고, `struct.Struct`를 미리 컴파일해 프레임마다 포맷 문자열을 재파싱하지 않는다.

## 3. 지터 제거: 1€ 필터를 양방향으로

프레임마다 독립 추정된 관절 위치는 잘게 떨린다. 고정 컷오프 저역통과를 걸면 떨림과 함께
빠른 동작까지 뭉갠다. 춤은 정지와 급발진이 번갈아 나오므로 최악의 입력이다.

[1€ 필터](https://gery.casiez.net/1euro/)(Casiez et al., CHI 2012)는 **신호 속도에 따라
컷오프를 바꾼다.** 멈춰 있으면 컷오프를 낮춰 강하게 억제하고, 빠르면 올려 지연을 줄인다.

```python
dx_hat  = a_d * dx + (1.0 - a_d) * self._dx_prev   # 속도 추정도 필터링한다
cutoff  = self.min_cutoff + self.beta * abs(dx_hat)  # 핵심
```

원래 실시간용 필터라 위상 지연이 남는데, 이 파이프라인은 오프라인이다. **정방향으로 걸고
역방향으로 한 번 더 걸면 지연이 상쇄된다.** 실시간이 아니라서 치를 비용이 없다.

적용 위치도 선택이다. 쿼터니언이 아니라 **리타겟 이전의 관절 위치**에 건다. 수치적으로
안정적이고 추출기 종류와 무관하게 공통으로 적용된다.

쿼터니언에 걸어야 할 때(회전을 직접 내는 추출기)는 함정이 하나 더 있다. `q`와 `-q`는 같은
회전이라 부호가 프레임마다 뒤집힐 수 있고, 그대로 성분을 필터링하면 뒤집힌 지점에서 회전이
크게 튄다. 앞 프레임과 같은 반구로 맞춘 뒤 걸고 마지막에 정규화한다.

기본값 `min_cutoff=4.0Hz, beta=2.0`은 측정으로 정했다. RMSE만 보면 `min_cutoff=8`이 낫지만
노이즈가 조금만 커져도 떨림이 되살아나서, 견고한 쪽을 택했다. **가장 좋은 값이 아니라 가장
안 무너지는 값을 고른 것이다.**

## 4. 골반이 원점이라 걷는 동작이 제자리걸음이 된다

MediaPipe world landmark는 **골반을 원점으로 정규화**한다. 그래서 골반은 사실상 안 움직인다
(측정 0.4cm). 결과는 두 가지 증상으로 나타나는데, 원인은 하나다.

- `センター`에 담을 전역 이동이 없다 → 걷는 동작이 제자리로 나온다
- 몸이 움직인 만큼이 발로 나타난다 → 접지 중에도 발이 미끄러진다

해법은 관점을 뒤집는 것이다. **접지한 발은 세계 좌표에서 멈춰 있다.** 발이 몸 대비 뒤로 간
만큼 몸이 앞으로 간 것이므로, 그 변화량을 누적하면 골반 궤적이 되고 같은 양을 발에서 빼면
접지 중 발이 고정된다. 하나의 가정으로 두 문제가 같이 풀린다.

| | 이전 | 이후 |
|---|---:|---:|
| `センター` 이동 | 0.4 cm | **41.2 cm** |
| 접지 중 미끄러짐 | 1.16 cm/프레임 | **0.66 cm/프레임** |

접지 판정 임계값(높이 10cm, 수직 속도 0.25m/s)에도 트레이드오프가 있다. 조이면 미끄러짐은
줄지만 접지 프레임이 34%까지 떨어지고, 나머지는 "직전 속도 유지"로 채워진다 — **근거 없이
이어 붙인 구간이다.** 현재 값에서 접지 74%, 미끄러짐 0.60cm/프레임.

지면 높이는 시퀀스 전체에서 발목이 가장 낮았던 값으로 추정한다. 골반 기준 좌표라 절대
높이를 알 수 없으니 그것이 유일한 단서다.

남는 한계는 명확하다. **점프는 못 푼다.** 두 발이 모두 뜨면 기준이 없고, 골반 기준 좌표에서
점프와 양 무릎 굽힘은 구분되지 않는다.

## 5. 리타겟에서 제일 아팠던 것 — 레스트포즈 각도

관절 위치에서 본 회전을 만들 때는 부모 로컬 좌표계에서 최단호(shortest-arc) 회전을 쓴다.
문제는 최단호를 재는 **기준**이다. 레스트포즈 방향이 대상 모델과 어긋나면 그 각도가
**모든 프레임에 상수로 얹힌다.** 한때 `足首`이 19.55° 어긋난 채였다.

그래서 `--pmx model.pmx`를 주면 레스트포즈 방향을 그 모델에서 직접 읽는다. A포즈 팔 각도는
표준이 40°지만 모델마다 다르다.

계층 구조에서 오는 함정도 있다. 목 기울기는 `頭`가 아니라 `首`에 넣어야 한다. MMD 표준
계층(`上半身2 → 首 → 頭`)에서 `頭`는 말단이라 회전을 줘도 자기 위치를 못 바꾼다. `頭`에
넣으면 목은 곧게 선 채 머리만 제자리에서 기운다.

그리고 MMD는 **없는 본을 조용히 무시한다.** 모션이 일부만 적용될 때 원인을 찾기 어려운
이유다. `--pmx`로 넘길 때 없는 본에 키를 찍고 있는지 미리 경고한다.

## 6. 키프레임 데시메이션 — 균등 샘플링을 버린 이유

리타겟은 모든 프레임에 키를 찍는다. 5분 영상이면 본 프레임 12만 개, VMD 14MB다. 대부분은
**MMD가 보간으로 만들어낼 수 있는 값**이라 파일만 키우고 수동 편집을 방해한다.

`--step`(균등 샘플링)은 정지 구간에서도 키를 남기고 급격한 동작에서도 똑같이 버린다.
대신 **지웠을 때 생기는 오차**를 재서 판단한다 — Douglas-Peucker의 회전판이다. 회전은
slerp로, 위치는 선형으로 보간해서 잰다. **MMD가 재생할 때 하는 것과 같은 계산이다.**

| | 키 감소 | VMD |
|---|---:|---:|
| 5분 영상 | 88% | 14.0 MB → 1.59 MB |
| 5초 클립 | 61% | 116 KB → 45 KB |

두 가지 최적화가 필요했다.

**청크 분할.** Douglas-Peucker는 각 점을 여러 구간에서 되풀이해 검사하므로 비용이 대략
(키 수 × 남는 키 수)로 는다. 5분 영상에서 10초가 걸렸다. `MAX_SPAN=512`로 잘라 처리하면 그
곱이 구간 크기로 묶여 선형에 가까워진다 — 같은 입력이 **0.6초**로 줄었고 품질은 사실상
그대로였다. 대가는 구간 경계에 강제로 남는 키인데, 5분 영상에 17개뿐이다.

**초월함수 제거.** 안쪽 루프에서 `acos`로 각도를, `sqrt`로 거리를 구하지 않는다. `1-|dot|`과
제곱거리를 임계값과 직접 견준다. 단조 관계라 순위와 판정은 같다.

허용치 1.0°는 위팔 끝점에서 4.9mm다. **1€ 필터가 이미 관절을 7.3mm 옮겨 놓았으므로** 그
아래면 새로 눈에 띌 이유가 없다. 앞 단계의 오차가 뒤 단계의 예산을 정한다.

## 7. MediaPipe vs GVHMR — 위치만 아는 것과 회전을 아는 것

MediaPipe는 프레임마다 독립적으로 관절 **위치**만 추정한다. GVHMR은 관절 **회전**을
파라미터로 직접 내고, 체형을 시퀀스 전체에서 고정하며, 세계 좌표 이동까지 낸다.

| | MediaPipe | GVHMR |
|---|---:|---:|
| 키를 찍는 본 | 18 | **24** |
| 본 회전 지터 (°/프레임) | 1.25 | **0.46** |
| 위팔 길이 변동 (cm) | 5.03 | **0.20** |
| 접지 중 발 미끄러짐 (cm/프레임) | 0.28 | **0.10** |

위팔 길이가 5cm씩 변한다는 건 **프레임마다 다른 사람을 보고 있다는 뜻**이다. 회전을 아는
추출기에서는 `頭`(머리 방향), `手首`(손등 방향), `肩`, `上半身2`에도 키가 찍힌다 — 관절
위치만으로는 정할 수 없던 본들이다. 점 하나뿐인 `head` 관절로는 머리가 어디를 보는지 알 수
없다.

대가는 속도다. M1에서 250프레임에 4분 29초. 그래서 추론은 파이프라인 밖에서 돌리고 결과
`.pt`만 읽어들인다.

여기서 조용한 함정이 하나. GVHMR 결과에는 **fps가 없다.** 함께 나오는 `0_input_video.mp4`는
30fps로 재인코딩된 것이라 믿을 수 없다. 원본이 25fps인데 30으로 읽으면 모션이 20% 빠르게
재생된다. `--source-video`로 원본을 같이 주는 이유다.

회전을 아는 시퀀스에는 스무딩이 **회전에만** 걸린다. 위치를 축별로 따로 거르면 관절이
제각기 움직여 뼈 길이(강체성)가 깨지기 때문이다.

## 8. 눈으로 봐야 원인을 안다

수치만으로는 리타겟이 맞는지 알기 어렵다. 그래서 브라우저 뷰어를 붙였다 — **원본 영상,
추출된 관절, 리타겟한 본 회전**을 같은 타임라인에 나란히 놓는다.

```bash
python -m autommd serve --pmx model.pmx    # http://127.0.0.1:8765
```

진단이 기계적으로 갈린다. 영상과 관절이 다르면 추출 문제, 관절과 본이 다르면 리타겟 문제다.

렌더링은 3D 라이브러리 없이 canvas 2D 투영으로 직접 짰다. 쿼터니언 곱셈과 FK 계산도 손으로
넣었다. 뷰어 하나 때문에 의존성을 늘릴 이유가 없고, `web/render.js`는 서버 뷰어와 파일 한
장짜리 정적 뷰어가 공유한다.

## 9. 표정 — 얼굴이 너무 작아서 한 프레임도 안 잡힌다

전신 영상에서 얼굴은 화면의 몇 %밖에 안 된다. FaceLandmarker를 그냥 돌리면 **1366×720
클립에서 0/150 프레임 검출**이다.

포즈 랜드마크로 머리 영역을 잘라 키운 뒤 넣으면 **247/250**이 된다. 대신 프레임마다 모델을
한 번 더 돌리므로 느려진다.

ARKit 52개 blendshape를 MMD 표준 모프(`まばたき` `ウィンク` `あ` `い` `う` `お` `にこり`
`笑い`)로 매핑하고, 기준선(하위 20분위수)을 빼고 0.05 미만은 데드존으로 버린다. 표정은
가만히 있을 때도 0이 아니라 작은 값으로 떠 있기 때문이다.

## 정리

만들면서 반복된 패턴이 몇 개 있다.

1. **좌표계 규약이 절반이다.** 골반 원점 정규화, 레스트포즈 각도, 쿼터니언 반구 — 실제
   버그는 대부분 알고리즘이 아니라 규약 불일치에서 나왔다.
2. **오프라인이라는 조건이 무기다.** 양방향 필터로 지연 0, 전체 시퀀스를 봐야 하는 지면 추정,
   전역 데시메이션 — 실시간이면 못 할 것들이다.
3. **앞 단계 오차가 뒤 단계 예산을 정한다.** 스무딩이 7.3mm 옮겼으니 데시메이션 허용치를
   4.9mm로 잡는 식이다. 단계별로 따로 최적화하면 이 관계가 안 보인다.
4. **기본값은 최적값이 아니라 견고한 값으로.** 노이즈가 2배가 돼도 안 무너지는 쪽.

다음은 로드맵의 world-grounded 추출기다. 점프 구간의 "직전 속도로 잇기"를 지우는 것이 목표다.
