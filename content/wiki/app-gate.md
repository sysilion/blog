같은 기능을 웹 브라우저에서는 막고 자사 앱에서만 열어주는 검사.
출석체크·룰렛처럼 리워드가 걸린 기능에 흔히 붙는다.

## 두 종류

판정을 **어디서** 하느냐로 갈리고, 이 차이가 곧 우회 가능 여부다.

| | 클라이언트 판정 | 서버 판정 |
| --- | --- | --- |
| 형태 | 페이지 JS 안의 조건문 | 서버가 렌더한 값 · API 응답 |
| 예 | `isApp: () => /TOKEN/.test(navigator.userAgent)` | `window.isApp = false;` 를 HTML 에 박아 내려줌 |
| 우회 | [[user-agent\|UA]] 를 맞추거나 변수를 덮어쓰면 통과 | 안 된다 — 값을 덮어써도 서버가 데이터를 안 준다 |

클라이언트 판정은 브라우저에 내려온 코드가 전부라서, 그 코드가 보는 값
(UA 문자열, 전역 변수)을 맞춰주면 그대로 지나간다.

서버 판정은 게이트가 두 겹이다. 화면의 분기를 뚫어도 그 뒤의 API 가 다시 거절한다.
앱이 보내는 헤더나 네이티브 로그인이 심는 쿠키를 확보하지 못하면 열 수 없다.

## 알아둘 것

**정적 HTML 과 런타임 DOM 의 값이 다를 수 있다.** `curl` 로 받은 소스에서는 빈 값인
플래그가 브라우저에서 실행하면 채워져 있다. 정적 소스만 보고 '게이트가 없다' 고
판단하면 반대 결론에 이른다. 판정 근거로 삼을 값은 **반드시 브라우저에서 읽어야 한다.**

**게이트가 없어 보여도 화면이 비어 있으면 그것도 게이트다.** 앱 웹뷰 전용 SPA 는
네이티브 브리지(`window.flutter_inappwebview` 등)가 없으면 라우트는 응답하지만
루트 엘리먼트가 빈 채로 남는다. 조건문이 아니라 렌더 실패로 막는 형태다.

우회가 가능하더라도 서버가 나중에 막을 수 있다. 자동화에 쓴다면 게이트에 걸렸을 때를
'실패' 가 아니라 별도 상태로 구분해 두는 편이 낫다 — 안 그러면 원인을 못 짚는다.
